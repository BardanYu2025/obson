## 本次实际代码处置

新文件`src/obson/babel/recovery_objectives.py`隔离四个native前缀目标。历史训练模块不修改，保留既有哈希和重放条件。

| 组 | 查询主损失Q | 17+结构S | 冻结源局部头的编码器监督L |
|---|---|---|---|
| baseline | 原权重 | 1.0 | 0 |
| without_remote | 原权重 | 0 | 0 |
| with_local | 原权重 | 1.0 | 0.25 |
| without_remote_with_local | 原权重 | 0 | 0.25 |

四组都计算同一个局部诊断值。关闭L时detach；开启时梯度经过冻结的原头进入编码器，头参数不更新。在相同预测/标签/mask下，baseline的实际优化值与原Context的Q+S一致，不能把不参与优化的局部诊断也加进旧loss日志。局部L沿用旧过去16根价格和活动目标，**不是纯近期价格损失**，不引入新头，也不改为未来预测。冻结头约束源接口，因此它带来的改善也不能独自证明增加了信息。

新测试验证：同一输入到loss函数时基线数值等价；四组分项数值相同；远端项不覆盖近16根而主查询覆盖；局部梯度进入编码器、不进入查询或头参数；四个因子的编码器梯度差；修改第80位置之后的行情不改变其四种loss；拒绝可训练/训练模式局部头。

这些是CPU合成样本上的9项测试，无真实权重、无优化器更新；**不是完整训练入口**。源局部头是否仍具备合格读取能力，四组的训练入口仍待实现；[V02/V14零更新资格](BABEL_RECOVERY_QUALIFICATION.md)现已单独提供数值、采样、目标、旧头检查和失败导出，真实CUDA待验。当前组件复用原history-query的native目标生成；它与Context的255条缓存目标路径在真实数据上的舍入一致性仍需预检，合成loss等价不证明整条真实流水线逐位相同。不能现在拿旧脚本开跑四组。
